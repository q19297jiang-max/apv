# Payment Card Tokenization

## Definition

Tokenization replaces sensitive cardholder data (PAN) with a non-sensitive equivalent (token) that can be used for payment processing without exposing the actual card number.

## Key Concepts

### Network Tokenization
**Source**: https://www.emvco.com/emv-technologies/payment-tokenization

- EMVCo standard
- Tokens generated by payment networks
- Universal across merchants
- Reduced fraud and chargebacks

### Acquirer Tokenization
**Source**: Industry standards

- Tokens generated by acquirer
- Merchant-specific
- Limited to acquirer network
- Scope reduction benefit

## Tokenization Architecture

```
Tokenization Flow:
├── Enrollment
│   ├── Card provisioning
│   ├── Token generation
│   └── Token-card mapping
├── Token Vault
│   ├── HSM-protected storage
│   ├── Token-to-PAN mapping
│   └── Cryptographic operations
├── Processing
│   ├── Token payment request
│   ├── Detokenization (in-flight)
│   ├── Authorization with PAN
│   └── Response with token
└── Lifecycle Management
    ├── Token update ( PAN change)
    ├── Token suspension
    └── Token deletion
```

## Token Format

**Source**: EMVCo Payment Tokenization Specification v2.0

```
Token: 1000000000000000000
├── First 6 digits: Token BIN (assigned by network)
├── Last 4 digits: Matches PAN last 4
├── Middle digits: Random, cryptographically generated
└── Check digit: Luhn algorithm
```

## Benefits

### Security
**Source**: PCI-DSS and EMVCo

- PAN never stored at merchant
- Tokens useless if stolen
- Reduced PCI-DSS scope (SAQ A-EP vs D)
- Protection against card-not-present fraud

### Operational
**Source**: Industry best practices

- Automatic card update (expiration, lost/stolen)
- Reduced chargebacks
- Improved authorization rates
- Better customer experience (card-on-file)
