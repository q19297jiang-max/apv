# APV V2 Authority Model

## Goal

Define which artifacts are canonical, how they are produced, and what kinds of edits are allowed.

## Canonical Project Data

The canonical project data for APV V2 is the set of markdown files and related project files stored in:

- `wiki/apv-v2/`
- `apv-projects/[customer]--[title]--[date]/`

Git versions the full artifact set for both surfaces.

## Authority Tiers

### Tier 0: Raw Source Authority

Definition:
- original customer documents
- original spreadsheets
- official regulation downloads
- official calculator captures
- vendor reference pages saved as evidence

Typical locations:
- `apv-projects/.../input/raw/`
- `apv-projects/.../evidence/`

Edit policy:
- never overwrite
- append new versions with dates when refreshed
- treat as immutable evidence

### Tier 1: Normalized Source Authority

Definition:
- markdown conversions of raw files
- extracted tables and summaries
- parsed questionnaires
- parsed volume/TPS summaries
- extracted requirement lists

Typical locations:
- `apv-projects/.../input/normalized/`

Edit policy:
- script-regenerated by default
- manual edits only when explicitly marked as corrected or annotated
- corrections must preserve traceability to raw sources

### Tier 2: Knowledge Authority

Definition:
- reusable knowledge pages
- compliance references
- infrastructure patterns
- pricing knowledge pages
- methodology documents

Typical locations:
- `wiki/apv-v2/knowledge/`
- `wiki/apv-v2/docs/`

Edit policy:
- curated and reviewable
- changes should cite source or evidence basis
- reusable knowledge is authoritative only within its documented freshness and scope

### Tier 3: Working Artifact Authority

Definition:
- compliance mappings
- architecture decisions
- sizing records
- pricing manifests
- assumption logs
- gap logs

Typical locations:
- `apv-projects/.../working/`

Edit policy:
- produced by scripts and skills
- may be manually corrected, but every correction should remain visible in git history
- these are authoritative for a specific run once verification gates pass

### Tier 4: Stage Output Authority

Definition:
- brainstorm report
- compliance report
- architecture report
- sizing report
- pricing report
- final response
- approval report

Typical locations:
- `apv-projects/.../outputs/`

Edit policy:
- produced by skill stages
- may be revised after review
- final submission authority exists only after approval gate passes

### Tier 5: Approval And Release Authority

Definition:
- approval checklist results
- verification reports
- release/package summaries

Typical locations:
- `apv-projects/.../approvals/`
- `apv-projects/.../verification/`

Edit policy:
- append or supersede, never silently replace
- reviewer decisions must remain auditable

## Non-Authoritative Artifacts

These are useful but not canonical:

- scratch notes without project references
- temporary exports
- caches
- local test output
- derived indexes such as embeddings or search caches

These may be regenerated and should never be treated as the source of truth.

## Manual Edit Rules

| Artifact Type | Manual Edits Allowed? | Rule |
|---------------|-----------------------|------|
| Raw source | No | Preserve original evidence |
| Normalized source | Limited | Only as explicit correction or annotation |
| Knowledge pages | Yes | Must preserve provenance and scope |
| Working artifacts | Yes | Allowed if traceable and reviewable |
| Stage outputs | Yes | Allowed during review/revision cycle |
| Approval artifacts | Limited | Only by explicit reviewer update |

## Canonical State Rule

The canonical APV V2 state is the git-tracked set of wiki and project artifacts, not a hidden database record, prompt history, or transient runtime cache.

## Implications

- every important step must leave a file artifact
- every approval-relevant claim must be traceable to evidence or knowledge pages
- every reusable update should be captured in markdown, not only in memory or prompt state
